# Release Playbook

The end-state: the engine published to npm as `push-to-comply`, and the
public repositories living in the `push-to-comply` GitHub organization
with clean histories:

| Repository                          | Contents                                    | Source in this monorepo        |
| ----------------------------------- | ------------------------------------------- | ------------------------------ |
| `push-to-comply/push-to-comply`     | This monorepo: engine, reference content, registry (`templates.json`), plugin marketplace | pushed as-is                   |
| `push-to-comply/soc2-template`      | The SOC 2 program template clients start from | generated by the export script |
| `push-to-comply/evidence-template`  | The engagement evidence-repo template       | generated by the export script |

## 0. Pre-flight (already automated)

`npm test` runs the engine suite, template integration tests, and the
export-script tests. The full client journey is rehearsed from a packed
tarball (see "Trying it out before the npm release" in the README) — do
this once more before the first publish:

```
npm pack --workspace push-to-comply
npm install -g ./push-to-comply-<version>.tgz
node scripts/export-repos.mjs
ptcomply init /tmp/rehearsal --template dist/repos/soc2-template --name "Test Co" --short-name TestCo
cd /tmp/rehearsal && npm install <path-to-tarball> && npx ptcomply validate && npx ptcomply build && npx ptcomply gaps
```

### Optional: full registry rehearsal with a local npm registry

The tarball flow doesn't exercise registry resolution. To rehearse the
*real* publish/install protocol without touching npmjs, run
[Verdaccio](https://verdaccio.org) locally:

```
mkdir /tmp/registry && cd /tmp/registry
cat > config.yaml <<'YAML'
storage: ./storage
auth: { htpasswd: { file: ./htpasswd } }
uplinks: { npmjs: { url: https://registry.npmjs.org/ } }
packages:
  'push-to-comply': { access: $all, publish: $all }
  '**': { access: $all, proxy: npmjs }
YAML
npx verdaccio --config config.yaml --listen 4873 &

cd <monorepo>
npm publish --workspace push-to-comply --registry http://localhost:4873 --//localhost:4873/:_authToken=fake

# The exact first-user experience, resolved through the registry:
export npm_config_registry=http://localhost:4873
cd /tmp && npx -y push-to-comply init acme --template <monorepo>/dist/repos/soc2-template --name "Test Co" --short-name TestCo
cd acme && npm install && npx ptcomply validate && npx ptcomply build && npx ptcomply gaps
```

(`--//localhost:4873/:_authToken=fake` satisfies npm's publish-needs-auth
check; the config accepts anonymous publishes. Unset
`npm_config_registry` afterwards.)

## 1. Publish the monorepo to the organization

Push this repository to `push-to-comply/push-to-comply`. For a clean
public history, start it fresh (the pmarkert repo keeps the full
development history):

```
git checkout main   # after merging the PR
git checkout --orphan public-main && git commit -m "push-to-comply <version>"
git remote add org git@github.com:push-to-comply/push-to-comply.git
git push org public-main:main
```

(Or push the full history as-is if you decide you want it public —
either works; `templates.json` and the plugin marketplace resolve from
this repo's main branch, so this repo must exist before `init` and
`/plugin marketplace add` work from the well-known locations.)

## 2. Publish the engine to npm

Option A — locally:

```
npm login
npm publish --workspace push-to-comply --access public
```

Option B — via CI: add an `NPM_TOKEN` secret (npm automation token) to the
org repo, then push a version tag (`git tag v0.1.0 && git push org v0.1.0`).
The `release.yaml` workflow verifies tests and the tag/version match, then
publishes with provenance.

## 3. Export and push the template repositories

```
node scripts/export-repos.mjs
cd dist/repos/soc2-template
git remote add origin git@github.com:push-to-comply/soc2-template.git && git push -u origin main
cd ../evidence-template
git remote add origin git@github.com:push-to-comply/evidence-template.git && git push -u origin main
```

Then, in GitHub settings for both template repos: mark **"Template
repository"** so "Use this template" works. Optionally, in the
soc2-template repo, run `npm install` once and commit the generated
`package-lock.json` for reproducible client installs.

## 4. Verify the public paths

- `npx push-to-comply init smoke-test` → registry loads from the org repo,
  clones `soc2-template`, and the scaffold builds.
- In Claude Code: `/plugin marketplace add push-to-comply/push-to-comply`
  and `/plugin install ptcomply@push-to-comply`.
- A clone of `soc2-template` with no local tooling: push a trivial content
  PR and confirm the CI + portal workflows run green.

## Subsequent releases

1. Bump `packages/push-to-comply/package.json` version; update ROADMAP.
2. Merge to main; tag `v<version>` (CI publishes to npm).
3. Re-run the export script and push the regenerated templates (each
   release is one new commit on the template repos: use
   `git -C dist/repos/soc2-template push --force-with-lease` only if you
   deliberately regenerate; otherwise commit updates onto the existing
   template history to preserve client-facing diffability).
